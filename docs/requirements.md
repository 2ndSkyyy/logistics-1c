# Соответствие заданию

Основание — предоставленное «ТЗ_Колледж 2025.pdf», общие требования и вариант **0293-01**: отчёт по оплатам заявок на СКД и обмен JSON. Исходный PDF в репозиторий не включён. Сверка обновлена 28.09.2026 по коммиту `74de3c7`, исходникам и ручным результатам автора.

**Вывод:** основной демонстрационный сценарий реализован и проверен. Полное соответствие всем требованиям пока не заявляется: остаётся расхождение типов реквизитов в расширении из Приложения 2. Установка текущего комплекта с нуля отдельно не подтверждена.

Для выбранного варианта 0293-01 они не являются отдельными обязательными отчётами/механизмами обмена. Учёт отправлений в самой заявке относится к общему заданию и присутствует.

## Расхождение типов: Приложение 2

| Реквизит | Логистика | Расширение Бухгалтерии |
|---|---|---|
| Логист | Ссылка на «Сотрудники» | Строка 150 |
| Отдел | Ссылка на «Отделы» | Строка 100 |
| Водитель | Ссылка на «Водители» | Строка 150 |
| Тягач | Ссылка на «Тягачи» | Строка 100 |
| Прицеп | Ссылка на «Прицепы» | Строка 100 |

Прямой JSON содержит UUID и представление справочного значения, но импорт в БП сохраняет только наименование. Это позволяет показать сведения, однако не сохраняет ссылочную модель. Работающий обмен не устраняет это расхождение с требованием.

Также отличаются допустимые знаки чисел: `СтавкаНДС`, `Оплаты.Сумма` и `ОтправкаДокументов.СтоимостьОтправления` в БП неотрицательные, а в логистике допускают любой знак. Для строгого соответствия квалификаторы следует согласовать. Служебные UUID и даты связи закономерно различаются по направлениям обмена.

Для закрытия пункта нужно добавить/сопоставить справочники в расширении, хранить внешний UUID, заменить строковые реквизиты ссылками, изменить импорт и мигрировать существующие данные в копии базы. Смена одного свойства «Тип» без обновления загрузчика недостаточна. После изменения требуется повторный обмен и проверка создания счёта.

## Уточнения области решения

- Состав бухгалтерских документов ограничен счетами; касса, возвраты и реализации не реализованы. Если проверяющий ожидает дополнительные виды документов, их состав следует согласовать.
- Обмен ручной, по одной сохранённой заявке; автосоздание заявки, массовая загрузка и расписание отсутствуют.
- Отчёт отражает текущую оплату заявок периода, не историческую задолженность. Частичная оплата относится к неоплаченным.
- Почтовые отправления учитываются вручную; интеграция с Почтой России не заявляется.
- Роли, фоновый обмен и банковский API в явных индивидуальных требованиях не указаны и в проекте не реализованы.

## Технические доработки

1. Привести типы и квалификаторы к согласованной модели и повторить ручные проверки.
2. Проверить установку из исходников в новой паре баз и заполненные строки отправлений/задолженности.
3. Убрать дублирование обмена между формами документов и обработками, выделив общую серверную логику.
4. Добавить проверки допустимых сумм и ставок: сейчас в логистике разрешены отрицательные ставки; значение −100 при расчёте без НДС приводит к нулевому знаменателю.
5. Проверить нулевые оплаты, ошибочные файлы и распределённые платежи по [плану тестирования](testing.md).

Параллельный импорт не защищён отдельной блокировкой уникальности; дата пакета не является полноценной версией документа. Эти ограничения важны при переходе от учебного сценария к многопользовательской работе.
