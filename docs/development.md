# Ход разработки и принятые решения

Это описание фактических этапов учебной работы 26–28 сентября 2026 года. Git подключается после разработки, поэтому перечисленные этапы не выдаются за ранее существовавшие коммиты.

## 1. Модель логистики

Создана самостоятельная конфигурация с семью справочниками: контрагенты, договоры, отделы, сотрудники, водители, тягачи и прицепы. Договор подчинён контрагенту; сотрудник содержит отдел. Центральный документ — «Заявка». В нём собраны маршрут, суммы, сроки, транспорт, оплаты, бухгалтерские документы, отправка документов и работа с задолженностью.

Расчёты и проверки даты маршрута/владельца договора размещены в модуле объекта `Заявка`, в `ПередЗаписью`. Поэтому они выполняются и при записи из формы, и при программной записи обработкой. Сумма оплаты равна итогу таблицы; остаток — разности стоимости и оплаты. Разница без НДС не является полноценной прибылью: прочие затраты проект не учитывает.

## 2. Расширение Бухгалтерии

Вместо изменения типовых модулей создано расширение «ЛогистикаОбмен» с собственным документом `ЛГ_Заявка`. Заимствованы необходимые типовые объекты. У счёта добавлена ссылка `ЛГ_ЗаявкаОснование`.

Организация, заказчик и договор в БП — её собственные ссылки. Для логиста и транспорта выбран упрощённый строковый перенос представлений; это сохраняет читаемость в БП, но не полную типизацию справочников логистики. Формальный разрыв с требованием задания вынесен в [requirements.md](requirements.md).

## 3. Счёт на основании заявки

Команда формы сохраняет заявку и открывает форму счёта с параметром `Основание`. Обработчик расширения перехватывает `ОбработкаЗаполнения` через `&Вместо`.

Для других оснований вызывается исходная процедура через `ПродолжитьВызов`. Для нашей заявки сначала используется стандартное заполнение шапки, затем устанавливаются организация/клиент/договор и одна строка перевозки. Записывается ссылка на заявку, необходимая для последующего поиска счетов.

При отладке временное диагностическое сообщение подтвердило вызов расширения; исполняемой диагностической остановки в текущем модуле нет. Для использовавшейся учебной базы проверяли безопасный режим расширения. Доступ к таблице уточнён как `ЭтотОбъект.Товары`. Поддержку ставки НДС проверяем по имеющимся значениям перечисления данной версии БП, а не молча подставляем произвольную ставку.

## 4. Прямой обмен JSON

Номера документов недостаточны для устойчивой связи между базами. Поэтому передаётся UUID исходной ссылки, а его отображаемый номер остаётся отдельным полем.

Сначала возникала ошибка «Не настроена выгрузка типа: Контрагент». Определение ссылочного значения исправлено через `Справочники.ТипВсеСсылки().СодержитТип`; ссылка превращается в JSON-объект с именем справочника, UUID и представлением.

Следующая ошибка указала на отсутствие `Выгрузка_Дата` в `ЛГ_Заявка`. Добавление реквизита и обновление базы согласовали метаданные приёмника с импортом. Выявилась необходимость проверять наличие полей, а не считать совпадение форм доказательством совпадения схемы.

## 5. Обратный обмен

Счета выбираются по явной ссылке на заявку. Для обратной передачи принят полный снимок: в файле весь актуальный набор счетов и оплат. Он проще частичных изменений и позволяет удалить из логистики оплату после отмены проведения банковского документа.

Перед записью проверяются направление, UUID, время пакета, стоимость, повторяющиеся идентификаторы и арифметика. Строки заменяются, а не дописываются — это основа повторной загрузки без роста суммы. Автоматическое разрешение конфликтов и очередь обмена не реализованы.

## 6. Банковские оплаты

Источник — строки расшифровки документа «Поступление на расчётный счёт». Связь проходит через счёт покупателю к заявке. В сумму попадает распределённая часть платежа, а не весь документ. Отбираются только проведённые поступления без пометки удаления для организации и заказчика заявки.

Проверен сценарий: 20 000 частично → ещё 30 000 → 50 000 полностью → отмена проведения второй оплаты → снова 20 000. Текущие приложенные JSON соответствуют последнему состоянию.

## 7. Отчёт СКД

Отчёт «Оплата заявок» группирует записи по статусу и отделу, выводит детали и суммирует стоимость, оплату и остаток. Первоначально у пользователя не было настроек периода. В запрос добавлены два параметра; они выведены в пользовательские настройки. Границы приводятся к началу и концу дня.

Решение показывает текущие суммы заявок, созданных в выбранном интервале. Для отчёта о задолженности на историческую дату нужна иная модель расчёта/хранения; текущий отчёт такой возможности не заявляет.

## 8. Отдельные обработки

Первые команды обмена создавались в формах заявок для отладки. Затем добавлены `ОбменJSON` в логистике и `ЛГ_ОбменJSON` в расширении — механизм обмена оформлен объектом «Обработка», как предусмотрено заданием.

Пользователь выбирает сохранённую заявку. Клиент отвечает за диалог и локальный файл; серверные функции получают документ по ссылке, проверяют и записывают его. Ссылка фиксируется до открытия файлового диалога. При успешной загрузке отдельная обработка записывает документ автоматически. Старые команды форм пока сохранены для совместимости, их код дублирует часть логики; дальнейшая доработка — единый серверный модуль и удаление дублирования после проверки.

## 9. Подготовка публикации

Первые попытки экспорта дали типовую Бухгалтерию вместо расширения. Проверка `Configuration.xml` установила ошибку по имени и составу объектов. Финальный архив содержит только нашу конфигурацию и расширение: 44 файла исходной поставки, около 0,52 МБ без сжатия.

При проверке полного исходного архива найдены три ошибки: отсутствующий обработчик изменения логиста, неверный тип телефона сотрудника и длина email 10 символов. Подготовлены исправления и отдельный короткий сценарий проверки. Исходники расширения и два примера JSON сохранены без изменения; список исправленных путей и хеши исходной поставки записаны в `source-origin.json`.

Документация различает подтверждённые ручные результаты, выводы из чтения кода и ещё не выполненные тесты. Публикация не означает автоматического соответствия всем формальным требованиям или готовности к эксплуатации на реальных данных.
